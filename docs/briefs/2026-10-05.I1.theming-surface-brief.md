# Brief: a theming surface for Firstmate's look and voice

Tracker: jroethel/firstmate#1 (Refs #1).
Date: 2026-10-05.
Stage: brainstorm output, consumed by /loop-plan.

## Outcome

Firstmate gets a theming surface.
A captain picks a look and a voice once per home, and everything Firstmate itself renders about the fleet follows it.
Layout, colors, and type are three independent axes, and light and dark are modes.
Presupposition check: the ask named "a retheme".
The real need is the surface, and specific themes are only the proof that it works.
Verdict: build the surface and ship two themes as evidence.

## End artifact

A pull request against the private copy (jroethel/firstmate) carrying the surface and two shipped themes.
The upstream branch cut from it carries the surface and Restrained only; the first LCARS moves to the home themes folder there, so upstream sees one neutral example and no trademark-flavored theme.
It is used from the private copy for a few days before a separate upstream submission to kunchenguid/firstmate, which this chain prepares as a branch but never opens.

## Done looks like

- You say "switch to Restrained, light" in chat; Firstmate edits the per-home setting and rebuilds, and the board opens in that state at the same address.
- On the laptop home the board opens compact; on the desk home it opens full; in the page you can flip layout and mode instantly.
- With no theme selected, every surface looks and reads exactly as today, including the reply `Captain, shipshape.`
- The repo's lint passes and `bin/fm-test-run.sh --changed` passes, covering the board build with each shipped theme.
- When you ask to sync with upstream, Firstmate hands you the two recorded git commands that merge upstream main into the fork's main and push it, and the existing update command then fast-forwards the home unchanged.

## Approach

### Chosen: a theme slot in the shipped board plus one small per-home selection

The template keeps its single data slot and gains a second slot where the build inlines the selected theme's stylesheet.
The page root gains layout and mode attributes that the build sets from the home's selection.
Layout rules live in the template and own geometry only: columns, density, sizes, radii.
A theme is a folder holding a stylesheet that defines colors for light and for dark plus the type pairing, and an optional voice line naming its no-op reply.
Shipped themes live beside the template.
The home's own themes live in a themes folder under its settings area and are found by name first.
Mode is light, dark, or auto following the system; layout is full or compact from the home setting; both are also instant in-page switches that start from the home's default.
Switching the theme itself is a setting change plus a rebuild, because an in-page theme switch would carry every theme's CSS and fonts in every board.
The session-start digest prints one theme line only when a theme is selected, carrying the selected name, the no-op reply, and the stylesheet path for fleet pages, so a home with no theme pays nothing and the always-loaded contract grows by two edited lines and nothing else.
A home theme is captain-owned and trusted for its design, but the build refuses one that could escape the page's markup or fetch remote content, because the board's script routes keyed answers back into Firstmate.
Fork sync is not a command: it is two git lines (fetch upstream, merge upstream main into the fork's main, push) recorded in the home's learnings, because anything under `bin/` enters the lint, coverage, and doc-audit sets that the upstream branch would then have to excise.

## Success criteria

1. `[executed-check]` With no selection present, the built board renders equivalently to today's build through the existing render harness (same badges, stat strip, and sections) and carries no theme block, and the session digest prints no theme line.
2. `[executed-check]` For each shipped theme and each of the four layout-by-mode combinations, the build succeeds, the built page declares the requested layout and mode, carries that theme's styles exactly once, and still carries its data exactly once.
3. `[executed-check]` A selection naming a theme that exists in neither place stops the build with a message naming the name and both folders searched, and nothing is written.
    A home theme containing a style-closing tag, an import rule, or a url() reference is refused the same way; shipped themes are exempt.
4. `[executed-check]` The repo's lint passes and `bin/fm-test-run.sh --changed` passes on the branch.
5. `[executed-check]` Every shipped combination renders in headless Chrome at 1280 and 390 pixels wide with no horizontal overflow, and the eight screenshots are in the PR body.
6. `[executed-check]` In Restrained, every checked text pair meets 4.5:1 and every border pair meets 3:1 in both modes, recomputed from the shipped stylesheet with the scout's contrast tool.
7. `[executed-check]` A theme that names a no-op reply makes that reply appear in the session digest; one that names none leaves the digest showing the default.
8. `[executed-check]` The two recorded sync commands, run on a fork main that carries one extra commit, end with fork main containing upstream main and that commit, with no force push and no rebase, and the existing update command then reports a fast-forward.
9. `[judgment]` The Restrained board reads as a calm Star Trek: The Next Generation descendant rather than a generic dark dashboard, in both modes.
    Reformulation attempted ("elbow and pill frame present") and rejected: it would pass a frame with none of the feel.
10. `[judgment]` An upstream maintainer reading the diff sees a theme slot and two examples, not a Star Trek retheme.
    Reformulated partway: no theme name, font, or hex value appears outside the two theme folders and their test.

## Seams

In blast-radius order, each independently checkable:

1. Theme selection and application: the board build reads the home's selection, finds the theme by name in the home first and the shipped set second, and applies it (criteria 1 to 4).
2. Layout and mode rules in the template: geometry-only full and compact, light and dark switching, in-page switches starting from the home default (criterion 5).
3. Shipped themes: Restrained in both modes with its type pairing, and the first LCARS as-is (criteria 5 and 6).
4. Voice: the two edited contract lines and the digest's theme line (criterion 7).
5. Fleet-page reach: the digest line's stylesheet pointer, which is all Firstmate-authored pages need (checked by criterion 7's digest read).
6. Recorded fork sync commands (criterion 8), fully independent of the others.

## Known vs guessed

### Verified this session

- The template is the only tracked HTML surface: 180 token uses, 34 hex values all in the root block, no dark mode, fonts from one import, and 52 raw-token uses on 35 component lines that bypass the semantic layer.
- The build reads one template, requires exactly one data slot, and writes one file at a stable path; the page's own JavaScript runs in Lavish and queues answers.
- `Captain, shipshape.` is specified in two AGENTS.md lines and one Pi example; no test pins it; AGENTS.md is at 6,888 words against the 9,000-word ceiling VISION.md states.
- The update command is origin-only and fast-forward-only, and it skips a diverged main; the fork and upstream are identical today.
- Calm has one on-or-off knob and hard-coded colors per harness.
- Upstream's vision text welcomes opt-in presentation features; the two closed look-and-feel PRs were closed by their own authors.

### Believed, unchecked

- The system light-or-dark query and in-page attribute switching behave inside Lavish's served frame as they did in the scout's headless tests.
  If wrong, auto mode falls back to the home's pinned mode and the in-page switches become a parked item.
- Lavish shows a rebuilt board on reload at the same address without a new session.
  If wrong, the switching story gains one "reopen" step.
- The Restrained tokens port onto the real board's classes with only the slot.
  If wrong, a few component rules move to semantic tokens, which is the planned fix anyway.

### Guessed

- An upstream maintainer prefers a slot with examples over a design-system refactor.
  If wrong, the semantic refactor becomes the follow-up they ask for, and the slot still stands.
- Two merged themes' CSS stays under a few hundred lines each.
  If wrong, nothing breaks; the "how easy" demonstration weakens.
