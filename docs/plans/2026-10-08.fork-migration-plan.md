## 1. Summary

The captain chose, on 2026-10-08, to replace the private standalone repository with a public true fork of upstream, and to make the fork's main a one-writer branch.
Only the project clone writes fork main, through workers and one landing action; the home only fast-forwards from the fork and is firewalled against commits; every upstream merge is an ordinary worker task on a branch.
GitHub's role is to show the delta against upstream and to run CI, not to perform merges.
The migration is eight steps plus one catch-up step this plan adds, because upstream moved after the reviews.
Steps 2 through 6 are outward-facing and wait for the captain's go; step 4 (the first public push) is the one irreversible step.
After the switch, four follow-on items finish the target: the home firewall, the upstream sync as a worker task with a one-action landing script, the runbook update in `docs/jr-fm-drift.md`, and the upstream contribution of the held session-lock fix.

### The seven scenarios, briefly

1. A worker change lands: spawn from the repository's main, commit on `fm/<id>`, `fm-merge-local.sh` fast-forwards the clone, Firstmate pushes, `/updatefirstmate` updates the home.
   It held every time (2026-10-06 four times through PRs, 2026-10-07 00:15 through a local landing), but it is three separate commands, and cleanup counts the work as landed before the push (`bin/fm-teardown.sh:72-74`), so a session that stops between land and push leaves the change only in the clone (inferred from the code, not observed).
2. An upstream sync runs in the home: the live checkout sat on the scratch branch for about two hours on 2026-10-07 and 25 minutes on 2026-10-08, and a worker was spawned inside the 2026-10-08 window.
   The final fast-forward changed instruction files under the live session (5 files on 2026-10-08, 25 including `AGENTS.md` on 2026-10-07), and rerere resolutions stay in the home's `.git/rr-cache` (3 entries).
3. `/updatefirstmate` fetches only `origin`; it calls a home that is merely ahead "diverged", and after an in-place sync it prints `already current` and `reread-firstmate: no` even though instructions changed.
   Session start never updates the home itself.
4. Direct commits in the home: 9 non-merge commits plus all 3 upstream merge commits were made in the home, and the home pushed on 2026-10-07 12:52 and 17:09 and 2026-10-08 09:04.
   One of them changed `bin/fm-spawn.sh` directly, outside the pipeline path.
5. The project clone does not refresh: its main moves only at a landing or a manual pull, and it trailed the repository by 36 commits until the 2026-10-08 09:39 landing.
   `fm-merge-local.sh` checks ancestry only against that stale main, so a branch the repository has moved past lands cleanly and then fails at push.
6. Another host (not observed, inferred): a host that runs its own sync makes a different merge commit for the same upstream and diverges; `pull --ff-only` and `fm-update.sh` both refuse.
7. Both writers at once (fired 2026-10-08): the home pushed its sync at 09:04:05 while a ready worker branch was built on the previous main, so that branch could no longer be pushed as it was; it was rebased at 09:37, landed at 09:39:45, and pushed at 09:39:49.

## 3. Decision record

The captain's answers, verbatim from the review board (2026-10-08 16:11):

- "Flow architecture decisions: Yes: rule, two hooks, no upstream remote; A worker task on a branch in the project clone; Keep local-only plus jr-fm-land.sh"
- "Flow architecture target: Public true fork now; keep the earlier target's merge path"

### D1. Firewall the home: yes, with the rule, two hooks, and no upstream remote

Not taken: `fw-rule` (the rule in the captain's preferences file only, nothing enforced) and `fw-none` (keep upstream's fleet-empty escape hatch and the two writers).
Rationale (first review): one accident, the home being a writer, produces every failure mode the map found except the identity one, so the fix is to make the home pull-only and enforce it with private state that adds no tracked drift against upstream.
The rule gives the explanation before any work is wasted, the hooks catch habit across every harness, script, and human, and the missing `upstream` remote removes the path that did the most damage.
Evidence: a throwaway-repository experiment (git 2.43.0) with `pre-commit` and `pre-merge-commit` hooks installed:

| Case                                                         | Result                                                             |
| ------------------------------------------------------------ | ------------------------------------------------------------------ |
| `git commit` of a direct edit                                | refused, exit 1                                                    |
| `git pull --ff-only origin main` from behind                 | fast-forwarded, exit 0, no hook ran                                |
| `git merge --ff-only origin/main` (the `fm-update.sh` shape) | fast-forwarded, exit 0, no hook ran                                |
| clean non-fast-forward `git merge`                           | refused by `pre-merge-commit`, exit 1, tree left staged, no commit |
| conflicted merge resolved, then `git commit`                 | refused by `pre-commit`, exit 1                                    |
| `git commit --no-verify`                                     | allowed, exit 0 (the deliberate emergency door)                    |

The review called it "a tripwire, not a wall": the rule is the policy, the hooks catch habit.
It overrides one upstream allowance for this home only, `AGENTS.md:47` (firstmate may change shared tracked material directly when the fleet is empty), and does so in the captain's private preferences file, because editing `AGENTS.md` in the fork would conflict on every sync.
The review rejected a second layer, a Claude permission guard on tracked paths: it binds one harness while this home also runs others, and it is a second rule set to keep in step with the first.

### D2. Where the upstream merge runs: a worker task on a branch in the project clone

Not taken: `merge-home` (keep it in the home with an idle-fleet check; keeps the second writer and failures F1, F2, F3, F6), `merge-third` (a third clone used only for syncs; one more place that trails), and the alternate target's GitHub-first merge (`target-fork-github-merge`: GitHub's Sync fork or the `merge-upstream` API, with a worker merge only on conflict).
Rationale: the merge becomes an ordinary change with one direction of travel (upstream, worker copy, clone main, fork, home), and the clone's rerere cache is shared by every worker copy.

GitHub's fork sync stops on any conflict (verified: the web flow prompts for a pull request on conflict, `gh repo sync` is fast-forward only, and the `merge-upstream` API answers 409 on a conflict), so the GitHub path would have been the exception path on 2 of the 3 refreshes so far.

The review's revisit condition: only if the fork's delta shrinks to files upstream rarely touches, for example after the retheme is offered upstream.
Also never use `gh repo sync --force`, which hard-resets fork main to upstream.

### D3. The "no PRs, remote repo" posture: keep local-only plus `jr-fm-land.sh`

Not taken: `mode-upstream` (also file an upstream issue proposing a delivery mode that lands locally and pushes main without a PR, so fleet sync and cleanup would refresh such a clone natively).
Rationale: `bin/jr-fm-land.sh` closes the land-then-push gap (A4, F4) and the stale-clone blind spot (A6, F5) without editing any upstream script, so drift against upstream grows only by `jr-fm-` scripts, a pattern the fork already carries.
Upstream scripts left untouched: `fm-update.sh`, `fm-ff-lib.sh`, `fm-merge-local.sh`, `fm-teardown.sh`, `fm-fleet-sync.sh`, `fm-spawn.sh`.

It explicitly replaces the first review's fork-identity answer.
Rationale: every row where the alternate target wins is a property of the fork identity, and every row where it loses is a property of the GitHub-performed merge, so take the identity and keep the worker merge.

## 4. Target architecture

Four invariants (first review):

- I1. Fork main has exactly one writer: `git push origin main` from the project clone, run by Firstmate as the second half of landing.
- I2. The home's tracked files change only by fast-forward from the fork through `/updatefirstmate`; the home never commits, merges, or pushes tracked files, while its gitignored `data/`, `state/`, `config/`, `.claude/settings.local.json`, and `.lavish/` stay freely editable.
- I3. Every tracked change, including an upstream merge, is a worker branch in a worker copy of the project clone, landed by fast-forward onto the clone's main.
- I4. After each landing, the clone's main equals fork main; after each `/updatefirstmate`, the home's main equals fork main.

```text
upstream    --(git merge upstream/main on the worker's own fm/<id> branch)-----------> worker copy
fork main   --(every spawn resets a worker copy)--------------------------------------> worker copy
worker copy --(jr-fm-land.sh: ancestry check against the fork, ff clone main, push)---> fork main
fork main   --(/updatefirstmate, ff only; hooks refuse commits; no upstream remote)---> the home
fork main   --(compare view and CI)---------------------------------------------------> GitHub
```

Components:

- `bin/jr-fm-land.sh <task-id>` (new, about a dozen lines plus a colocated test): fetch origin, refuse unless `origin/main` is an ancestor of the task's recorded branch, run `bin/fm-merge-local.sh <task-id>`, push the clone's main to origin, and print the `/updatefirstmate` reminder.
- `bin/jr-fm-sync-upstream.sh` (rewritten branch-local): run on a worker's `fm/<id>` branch, it fetches upstream, surveys what upstream added (today's step 1, with the optional keyword search), merges `upstream/main` into the current branch, stages resolved files and commits the merge on rerun, runs the doc audit, lint, and the tests for files both sides changed, and stops; it refuses on `main`; today's step 3 and the `.git/jr-fm-sync` markers are deleted because publishing is the ordinary landing and the task branch is the state.
- The home firewall (private, nothing tracked): two hooks in the home's `.git/hooks`, no `upstream` remote in the home, and the rules in the captain's preferences file.
- GitHub: the compare view `https://github.com/kunchenguid/firstmate/compare/main...jroethel:main` shows the delta, CI runs on every push to main, and `docs/jr-fm-drift.md` keeps the why.
- Upstream contributions: a second local clone `projects/firstmate-upstream` whose origin is upstream, initialized with `no-mistakes init --fork-url https://github.com/jroethel/firstmate.git`, so the pipeline pushes the branch to the one fork and opens the PR against upstream.

Rules for the captain's private preferences file, recorded by Firstmate in follow-on F2:

- The home is pull-only: its tracked files change only through `/updatefirstmate`; every other change is a worker task in the project clone.
- Landing a Firstmate change is `bin/jr-fm-land.sh <id>` followed by `/updatefirstmate`; never a raw `git pull` in the home.
- The upstream merge is a worker task whose brief says: run `bin/jr-fm-sync-upstream.sh` on the task branch, resolve conflicts by `docs/jr-fm-drift.md`, and add a ledger row for each new choice.

## 5. The migration

### Who fires what

Firstmate runs every command itself, as the captain prefers.
Every step that changes GitHub is outward-facing and waits for the captain's explicit go; Firstmate stages the exact command, reports the blast radius, runs it on the go, and verifies.
Step 4 is the one irreversible step: once the delta is public, assume it is copied and indexed.
Worker steps (1, 1b) are local-only ship tasks; their landing uses today's path for the last times (land with `bin/fm-merge-local.sh`, then push the clone's main, which the captain's land-means-push approval covers).

### Ordering constraints

- Step 1 (scrub and history check) and step 1b (catch-up) finish and land before step 2.
- The fleet stays idle on the Firstmate project from the start of step 2 until step 4 verifies: no spawn, no landing, no `/updatefirstmate`, no upstream sync.
  Between steps 2 and 3, `origin` still redirects to the renamed private repository, so a push would land there.
  Between steps 3 and 4, fork main is pure upstream, so a spawn would start a worker without the captain's delta and `/updatefirstmate` would report the home diverged.
- Run steps 2, 3, 5, and 4 in one sitting, in that order: step 5 has no dependency on step 4, and enabling Actions first makes step 4's push the fork's first CI run (no workflow here has a schedule trigger, so enabling Actions starts nothing by itself).
- Step 6 runs before anything else creates an issue or a PR on the fork, so issue numbers keep parity with the private repository (a PR to upstream lives on upstream and does not consume a fork number).
- Step 1's history check is re-run on the exact commit pushed in step 4, immediately before the push.
- Follow-on F1 to F4 run after step 8.

### Step 1. Scrub three documents and check the whole history (worker, local-only)

One worker task on the Firstmate project, local-only, landed with today's path.
Part a: replace the absolute home paths in the three jrit-loop documents named in D4 with repo-relative or home-relative wording (relative to the home root, such as `data/...`, never naming the home directory), changing nothing else.
Part b: the whole-history publication check, read-only, run in the worker copy after part a is committed, writing findings only to `$OUT` (private, never tracked), never to the repository:

```sh
git fetch upstream
mkdir -p "$OUT"
RANGE=upstream/main..HEAD          # every commit step 4 would publish that upstream does not already have
gitleaks git --log-opts="$RANGE --remerge-diff" --redact --report-format json --report-path "$OUT/gitleaks.json" .
git log -p --remerge-diff --format='commit %H%nauthor %an <%ae>%ncommitter %cn <%ce>%n%n%B' "$RANGE" > "$OUT/fork-history.txt"
E=$(git config user.email)
grep -nF -e "$HOME" -e "$(id -un)" -e "$(hostname)" -e "$E" -e "@${E#*@}" -e "$(basename "$H")" "$OUT/fork-history.txt" | cut -c1-160 > "$OUT/private-hits.txt"
git grep -nF -e "$HOME" -e "$(id -un)" -e "$(hostname)" -e "@${E#*@}" -e "$(basename "$H")" HEAD -- . > "$OUT/tree-hits.txt" || true
wc -l "$OUT/private-hits.txt" "$OUT/tree-hits.txt"
```

Issue and PR text also becomes public in step 6, so the same patterns are checked there: dump each of the 17 numbers with `gh-axi api repos/$FORK/issues/<n> --full` (the private repository's name until step 2; `$OLD` after it) into `$OUT/issue-text.txt` and grep it the same way.
Known expected hits, by category rather than count: the diff lines of the three documents' earlier versions (42 on 2026-10-08); the author, committer, and `Co-authored-by` lines carrying the work address on every fork-only commit, including the ones steps 1 and 1b add (the PR-merged commits carry it only as a trailer); the 2 diff lines of an earlier `docs/jr-fm-drift.md` naming the home directory as `~/<home directory>`; and one private marker in the body of PR #10 (step 6 re-creates that number from its title only).
Verify: gitleaks reports 0 findings; `tree-hits.txt` is empty after part a; `private-hits.txt` contains no line outside those categories.
Gate, the captain's call:

- Any gitleaks finding, or any private hit outside the known set: stop and report; a real secret must be rotated before anything is published, whatever else is decided.
- The known set: publish history carrying it (recommended), or rewrite.
  Rewriting means running `git filter-repo` on a copy, pushing the rewritten main to the new fork in step 4, and hard-resetting the home and the clone to it; every commit SHA cited in docs, reports, and backlog notes changes, the reset is destructive in both checkouts, and the captain's rule forbids rewriting pushed history, so the recommendation is to accept the known set unless a secret appears.

Rollback: part a is undone by a revert commit landed the same way; part b changes nothing.

### Step 1b. Catch up with upstream (worker, local-only)

Why it exists: the alternate review's precondition for step 4, "upstream main is an ancestor of the captain's main, so the push is a fast-forward", stopped holding after the reviews.
Re-checked 2026-10-08 with the compare API: upstream main moved from b062eb94 to 19fcbbde, one commit touching `tests/fm-watcher-lock.test.sh`.
A fork created in step 3 starts with upstream's current main, so the captain's main must already contain it, or step 4's push is refused as non-fast-forward.
One worker task on the Firstmate project, local-only, the captain's chosen merge location (D2) done by hand because the branch-local script does not exist yet:

```sh

git merge --no-edit upstream/main      # on the worker's own fm/<id> branch; resolve conflicts by docs/jr-fm-drift.md

# plus, for each file both sides changed since the merge base, its own test (the overlap rule in bin/jr-fm-sync-upstream.sh:87-106):
env -u DISABLE_AUTOUPDATER -u TYPESAFE_API_KEY bash bin/fm-test-run.sh --exclude-family real-herdr-gated <tests>
```

Land with today's path, then `/updatefirstmate` in the home.
Verify, immediately before step 2:

